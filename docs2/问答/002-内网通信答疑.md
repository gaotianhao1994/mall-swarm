# Q002：跨云厂商 / 跨账户内网通信 — 可行性分析与实战

> **前置阅读**: [001-内网通信.md](./001-内网通信.md)
> **背景**: 我们的 3 台服务器分布在 **2 个云厂商 + 2 个腾讯云账户** 下，能否走内网通信？

## 二、不同云厂商（腾讯云 vs 阿里云）能否内网通信？

### 结论：**不能直接内网通信** ❌

### 知识点：为什么跨厂商无法内网？

#### 是什么？

每家云厂商的"内网"其实是各自机房内部的**私有网络（VPC - Virtual Private Cloud）**。
这些 VPC 就像一栋栋独立的办公楼：

```
【腾讯云机房】              【阿里云机房】
┌─────────────────┐       ┌─────────────────┐
│   腾讯云 VPC     │       │   阿里云 VPC     │
│                 │       │                 │
│  172.16.x.x     │       │  10.0.x.x       │
│  (腾讯云内网)    │       │  (阿里云内网)    │
│       │         │       │       │         │
│   ┌───┴───┐     │       │   ┌───┴───┐     │
│   │服务器① │     │       │   │服务器③ │     │
│   │服务器② │     │       │   └───────┘     │
│   └───────┘     │       │                 │
│                 │       │                 │
│  ⚠️ 这是一栋封闭的大楼   │  ⚠️ 这是另一栋封闭的大楼  │
│  外面的进不来            │  外面的进不来             │
└─────────────────┘       └─────────────────┘
         ↕                         ↕
    完全隔离！两栋楼之间没有内部通道
```

#### 为什么？

| 技术原因 | 解释 |
|---------|------|
| **IP 地址段不重叠但不路由** | 腾讯云用 `172.16.x.x`，阿里云用 `10.0.x.x`，地址不冲突，但**没有物理链路连接两个 VPC** |
| **底层网络设备独立** | 每家的交换机、路由器、SDN 控制平面都是自建的，互不打通 |
| **安全隔离设计** | 云厂商故意不打通，防止跨租户攻击和数据泄露 |
| **商业竞争** | 腾讯云不会帮阿里云建通道，反之亦然 |

#### 追问：那有没有办法强行打通？

> 有技术方案，但对我们的场景来说**完全没必要且成本过高**。

| 方案 | 原理 | 成本 | 复杂度 | 是否推荐 |
|------|------|------|--------|---------|
| **公网 IP 直连** | 直接用公网 IP 通信 | 公网流量费 | 零 | ✅ **我们实际用的就是这个** |
| **VPN 网关** | 在两朵云间建立加密隧道 | VPN 网关费 + 流量费 | 中等 | 仅企业级混合云场景 |
| **专线接入** | 物理光纤直连两朵云机房 | 数万/月 + 工期数周 | 极高 | 金融/大厂才用 |
| **云联网/云企业网** | 各自的跨地域组网产品 | 按流量计费 | 高 | 同厂商跨区域用，跨厂商不行 |

**对于我们的 3 台小服务器来说，腾讯云 ↔ 阿里云之间的通信直接走公网即可。**
延迟差异约 20-30ms，对商城系统完全可以接受。

## 三、同厂商不同账户（两台腾讯云）能否内网通信？

### 结论：**默认不能，但可以配置打通** ⚠️

### 知识点：云账户隔离机制

#### 是什么？

云厂商的**账户（Account）= 租户（Tenant）**。每个账户的资源天然隔离：

```
【腾讯云】
├── 账户 A（你原来的）
│   ├── VPC-A (如 vpc-xxxx1)
│   │   ├── 子网: 172.16.0.0/16
│   │   └── 服务器 ①: 106.53.106.41 (内网 172.16.x.x)
│   └── 安全组、ACL 等
│
└── 账户 B（你新开的）
    ├── VPC-B (如 vpc-xxxx2)
    │   ├── 子网: 172.16.0.0/16 (或别的段)
    │   └── 服务器 ②: 106.53.132.192 (内网 172.16.y.y)
    └── 安全组、ACL 等

⚠️ 即使 IP 段相同，VPC-A 和 VPC-B 也是完全隔离的两个虚拟网络
```

#### 为什么隔离？

| 原因 | 说明 |
|------|------|
| **多租户安全** | 防止账户 A 的流量嗅探/攻击账户 B |
| **资源计费隔离** | 每个账户独立结算，资源边界清晰 |
| **权限隔离** | 账户 A 的管理员看不到账户 B 的资源 |

### 追问：怎么打通同厂商不同账户的内网？

> **官方方案：跨账户 VPC 对等连接（VPC Peering）**

#### 方案原理

```
打通前:
  账户A-VPC ──✕── 账户B-VPC    (隔离)

打通后:
  账户A-VPC ═══╤═══ 账户B-VPC    (对等连接)
               │
           虚拟专线(逻辑层面)
```

#### 腾讯云跨账户对等连接配置步骤

```
步骤 1: 在账户 A 的 VPC 上发起对等连接请求
  控制台 → 私有网络 → 对等连接 → 新建 → 选择"跨账户"
  → 填入账户 B 的 UIN（账号 ID）和 VPC-B 的 ID

步骤 2: 在账户 B 的控制台接受请求
  控制台 → 私有网络 → 对等连接 → 查看待接受请求 → 接受

步骤 3: 配置路由表（两边都要配）
  账户A路由表: 目标 172.16.y.y/16 → 下一跳 = 对等连接
  账户B路由表: 目标 172.16.x.x/16 → 下一跳 = 对等连接

步骤 4: 配置安全组放行
  两边的安全组都要允许对方内网网段的入站规则

步骤 5: 测试连通性
  ping 对方内网 IP
```

#### 前提条件与限制

| 条件 | 要求 |
|------|------|
| **同一地域** | 两台服务器必须在**同一个地域**（如同为"广州"或同为"上海"） |
| **IP 段不冲突** | 两个 VPC 的内网网段不能重叠（如都是 `172.16.0.0/16` 则冲突） |
| **账户状态正常** | 两个账户都没有欠费/封禁 |
| **费用** | 腾讯云 VPC 对等连接本身免费，但**跨账户流量按量收费** |

#### ⚠️ 重要提醒：对我们的场景是否值得做？

| 因素 | 分析 |
|------|------|
| 两台服务器是否同地域？ | **需要确认**（如果都是广州地域则可以） |
| 内网通信频率 | Gateway → Admin/Auth 会频繁调用 |
| 配置复杂度 | 需要在两个账户的控制台操作 ~15 分钟 |
| 收益 vs 成本 | 省去公网流量费 + 降低延迟 ~20ms |
| **建议** | 如果同地域，**值得做**；如果跨地域，没意义（跨地域对等连接也要收费且延迟不比公网好多少） |

## 四、判断能否内网通信的标准清单

在尝试让两台服务器内网通信之前，先逐项检查：

### 4.1 快速判断流程图

```
                    两台服务器要通信
                         │
                         ▼
                同一个云厂商吗？
                   ╱         ╲
                 是             否 → ❌ 只能走公网
                 │
                 ▼
            同一个账户？
              ╱     ╲
            是       否
            │         │
            ▼         ▼
        同一个 VPC？  跨账户对等连接
          ╱   ╲         │
        是     否        │
        │      │         │
        ▼      ▼         ▼
      ✅ 直接通  同账户   配置后可通
              不同VPC    (需同地域+网段不冲突)
              → 对等连接
```

### 4.2 技术检查清单

| # | 检查项 | 命令/方法 | 通过标准 |
|---|--------|---------|---------|
| 1 | **确认内网 IP** | `hostname -I` | 获取到 `10.x` / `172.16-31.x` / `192.168.x` 类地址 |
| 2 | **确认所属 VPC** | 云控制台 → 私有网络详情 | 记下 VPC 名称和 ID |
| 3 | **确认地域** | 云控制台 → 服务器实例详情 | 如"华南地区(广州)" |
| 4 | **确认 IP 段冲突** | 对比两台机器的 CIDR | 不能完全相同（如都是 `/16` 且前两段一样则冲突） |
| 5 | **安全组规则** | 云控制台 → 安全组 | 放行目标端口 + 对方网段 |
| 6 | **防火墙(iptables)** | `sudo iptables -L -n` | 没有 DROP 规则拦截 |
| 7 | **子网内可达性** | 同 VPC 内其他机器 ping 测试 | 同 VPC 内应该能通 |

## 五、内网通信测试方法

### 5.1 从服务器 ① 测试到服务器 ② 的连通性

```bash
# ===== 第 1 步：获取双方的内网 IP =====
# 在服务器 ① 上执行
hostname -I
# 输出示例: 106.53.106.41 172.16.18.5
#                  ^公网IP      ^内网IP ← 记住这个

# 在服务器 ② 上执行
hostname -I
# 输出示例: 106.53.132.192 172.16.20.3
#                     ^公网IP        ^内网IP ← 记住这个


# ===== 第 2 步：基础连通性测试（ping）=====
# 从 ① ping ② 的内网 IP
ping -c 4 172.16.20.3

# 结果解读:
#   64 bytes from 172.16.20.3: icmp_seq=1 ttl=64 time=0.8ms  ← ✅ 通了！内网可用
#   Destination Host Unreachable                              ← ❌ 不通，见排查流程
#   Request timeout                                          ← ❌ 超时，可能是安全组/防火墙拦截


# ===== 第 3 步：端口可达性测试（telnet）=====
# 测试 MySQL 端口是否可达
telnet 172.16.20.3 3306

# 结果解读:
#   Connected to 172.16.20.3          ← ✅ 端口可达
#   Connection refused               ← ❌ 端口未开放（服务没启动）
#   Timeout                          ← ❌ 端口被安全组/防火墙拦截


# ===== 第 4 步：批量端口扫描（nc 命令）=====
# 快速检测多个常用端口
for port in 22 80 3306 6379 8848 8080 8201 8401; do
  echo -n "Port $port: "
  (echo > /dev/tcp/172.16.20.3/$port) 2>/dev/null && echo "OPEN" || echo "CLOSED"
done

# 输出示例:
#   Port 22: OPEN      ← SSH
#   Port 3306: OPEN    ← MySQL
#   Port 6379: CLOSED  ← Redis 未启动或被拦截
#   Port 8848: OPEN    ← Nacos


# ===== 第 5 步：追踪路由路径（traceroute/mtr）=====
# 查看数据包走的路径
mtr -r 172.16.20.3

# 结果解读:
#   如果只经过 1-2 跳就到达 → ✅ 内网直达
#   如果经过很多跳且有公网 IP 出现 → ❌ 其实走的是公网
```

### 5.2 测试结果速查表

| 测试命令 | 正常结果 | 异常结果 | 可能原因 |
|---------|---------|---------|---------|
| `ping 内网IP` | `time<5ms`, 0% 丢包 | `Unreachable` / `Timeout` | 不在同一 VPC / 安全组未放行 ICMP / 防火墙拦截 |
| `telnet 内网IP 端口` | `Connected` | `Timeout` / `Refused` | 安全组未放行该端口 / 服务未监听 / iptables 拦截 |
| `curl http://内网IP:端口` | 返回 HTTP 内容 | 连接失败 | 应用层问题（服务挂了 / 端口映射错误） |

### 5.3 故障排查流程

```
ping 不通？
  │
  ├─→ 确认 IP 是否正确（是不是把公网当内网了？）
  │
  ├─→ 确认是否同 VPC（控制台查看）
  │     └─→ 不是 → 需要 VPC 对等连接 或 用公网代替
  │
  ├─→ 检查安全组（控制台 → 安全组 → 入站规则）
  │     └─→ 确保有允许对方网段的 ALL ICMP 规则
  │
  ├─→ 检查操作系统防火墙
  │     sudo ufw status          # Ubuntu 默认防火墙
  │     sudo iptables -L -n      # iptables 规则
  │     └─→ 放行: ufw allow from 172.16.20.0/24
  │
  └─→ 检查子网路由表
        ip route show
        └─→ 确认目标网段的路由下一跳正确
```

## 六、内网通信 vs 公网通信 — 完整对比

### 6.1 多维度对比

| 维度 | 内网通信 | 公网通信 |
|------|---------|---------|
| **安全性** | 数据不出机房，外部无法嗅探 | 经过公共网络，存在被截获风险（HTTPS 可缓解） |
| **延迟** | **1-5ms**（同城同机房） | **20-50ms**（取决于距离和网络状况） |
| **带宽** | 1-10 Gbps（几乎无限） | 取决于服务器公网带宽（通常 1-5 Mbps） |
| **稳定性** | 极稳定，几乎不丢包 | 可能受运营商线路波动影响 |
| **费用** | **免费**（同 VPC 内）/ 低费（对等连接） | **按流量计费**（约 0.8 元/GB） |
| **配置复杂度** | 需配置 VPC/安全组/路由 | 零配置，只要有公网 IP 就能用 |
| **适用场景** | 服务间高频调用（RPC/数据库） | 用户访问入口 / 低频跨云调用 |

### 6.2 针对我们 3 台服务器的架构建议

```
┌──────────────────────────────────────────────────────────────┐
│                                                              │
│  ① 腾讯云(A)  ═══ ? ═══  ② 腾讯云(B)                       │
│  网关服务器          数据服务器                                │
│                                                              │
│  情况分析:                                                    │
│  ├─ 如果同地域 + 同/可打通VPC → 用内网 IP 通信 ✅ 推荐        │
│  └─ 如果跨地域 / 不想配对等连接 → 用公网 IP 通信 ✅ 也行      │
│                                                              │
│  ①/② 腾讯云  ──✕──  ③ 阿里云                               │
│                                                              │
│  情况分析:                                                    │
│  └─ 不同厂商 → 无法内网 → 只能用公网 IP 通信 ✅ 唯一选择      │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 6.3 最终推荐方案

```
通信路径                          推荐方式    原因
─────────────────────────────────────────────────────
用户 → Nginx(:80)                 公网        必须公网，用户在互联网上
Nginx → Gateway(:8201)            Docker服务名  同机器容器间，bridge 网络
Gateway → Nacos(:8848)            Docker服务名  同机器容器间
Gateway → Admin(:8080)            公网IP       跨机器(①→②)，频率中等
Gateway → Auth(:8401)             公网IP       跨机器(①→②)，频率中等
Admin → MySQL(:3306)              Docker服务名  同机器容器间(②上)
Admin → Redis(:6379)              Docker服务名  同机器容器间(②上)
Portal → MongoDB(:27017)          Docker服务名  同机器容器间(③上)
Search → ES(:9200)                Docker服务名  同机器容器间(③上)
Portal → RabbitMQ(:5672)          Docker服务名  同机器容器间(③上)
各服务注册 Nacos                   公网IP       ②/③ → ① 的 Nacos
```

> **核心原则**: 同一台机器上的容器之间用 Docker 服务名（最快），跨机器之间用公网 IP（最简单）。等后续业务量大了再考虑 VPC 对等连接优化。

## 一句话总结

> **同厂商同账户同 VPC = 天然内网互通；同厂商不同账户 = 可以配对等连接打通；不同厂商 = 别想了，走公网吧。**
>
> **对我们而言：先用公网跑起来，优化的事以后再说。**
